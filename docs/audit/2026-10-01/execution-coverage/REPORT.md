# Quest execution evidence correction

The live Zeppelin Debris stall exposed a gap in what the old quest audit called proven. Reaching an objective area, generating a profile and supplying simulated inventory or quest state do not prove that the required action executes and receives an acknowledgement. This change retains the old six-class ledger as historical observation evidence and adds a separate execution grade bound to exact quest/objective semantics.

The primary-source inventory covers exactly4,335 unique quest IDs. It withdraws the end-to-end interpretation of3,028 GENERIC-PROVEN and2 STRATEGY-PROVEN entries: all3,030 are EXECUTION-UNVERIFIED until appropriate complete lifecycle contracts exist. The921 data-incomplete,311 source-uncertain,16 live-acceptance and57 unsupported-scripted classifications remain. This is a correction to proof claims, not a claim that3,030 quests were newly observed failing. No valid repair, runtime strategy, quest or historical test result is removed.

`objective-primitive-ids.json` gives exact required, candidate-source and tested IDs for every declared primitive family. Candidate item sources are OR alternatives, never a claim that every alternative must run or that a drop table alone supplies acquisition. Scripted target types, gossip, escort and vehicle/transport behavior remain explicitly unmapped where the inspected source does not establish them. The primary npc_vendor table is unavailable and is not treated as authoritative empty data. The gzip ledger preserves each quest's original class, required semantics, missing execution keys, acquisition alternatives and source limitations.

An execution contract must bind source files, a trace, named cases and exact semantic members. Required stages include admission, planning, travel, live acquisition, safe approach, dispatch, acknowledgement, authoritative progress, reacquisition, bounded recovery, objective completion, ender travel, turn-in dispatch/acknowledgement and next scheduling. No contract is accepted for the current dataset merely because a coordinate or PASS string exists.

Review of the initial validator found nine false positives. It could union partial stages across unrelated cases, accept out-of-order progress/completion, borrow another case's acknowledgement, count repeated or disconnected counter changes, and admit another collection action without a fresh live-target approach. New tests reproduced nine assertion failures before the repair. The unchanged focused tests now pass31/31, and the complete Python audit suite passes452 tests with one expected skip. Positive controls retain independently interleaved cases, real repeated acquisition and later contiguous observations of the same acknowledged action. These are receipt-validator tests; they do not certify real gameplay.

Each member now requires a complete lifecycle inside one case, stage prerequisites in that case, matching action identities, a continuous observed counter and fresh acquisition/approach before subsequent collection dispatch. Source and trace files must match their recorded hashes. This does not make fabricated input trustworthy: review the actual source/test producer and preserve the boundary between controlled observations and live original-client evidence.

This focused PR changes only Python audit tooling, tests and evidence. It does not contain the pending ground landing/loot/watchdog C# changes or the staged Rogue Cold Blood repair. The coupled ground lifecycle test remains held before execution, and native turn-in acknowledgement remains unproven. No blocked test is rerun through this branch or its hosted workflows. PR82 is already merged at eae93b1f; production deployment status remains separate from this evidence correction.
