# Execution inventory byte and membership integrity

Two published execution-audit JSON files had checksum declarations for their original Windows CRLF bytes while Git contained LF bytes. The compressed ledger still retained CRLF. Quest IDs, source semantics and classifications were unchanged, but a verifier could not use the summary to verify all published outputs consistently.

Write new inventory outputs as explicit UTF-8/LF bytes, and hash the logical bytes before optional gzip storage. The new verification command accepts exactly one plain or compressed representation of each of the three declared outputs, verifies its actual content hash, and reconciles all quest IDs, classifications, required/candidate/tested family membership, missing primitive keys and semantic hashes against the ledger. Conflicting representations, unknown output paths, duplicate/omitted/reassigned IDs and invented tested membership are rejected. Integrity verification is not a gameplay or live-completion certificate; source and causal trace validation remain separate mandatory gates for execution contracts.

The actual pinned TrinityCore335 source inventory was regenerated. Every one of the4335 ledger rows, every primitive family and the full classification partition reproduce unchanged after newline normalization. The original summary is retained in original-summary.json, and serialization-correction.json records both historical generated hashes and the published canonical hashes. No runtime code, native API, quest knowledge/strategy, class routine or quest classification is changed by this scope.

Tests exercise actual written bytes, gzip/plain identity, unchanged input objects, stale byte hashes, duplicate ledger IDs, incorrect partitions, foreign or unproven family members, changed source semantics, manifest path names and overwrite prevention.
